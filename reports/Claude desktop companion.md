# Build a hook-driven robot that speaks for Claude

Sev's companion should be an **Electron + three.js transparent overlay that listens to Claude Code's native `http` hooks on a loopback port**, renders an original boxy console robot exported from Blender as a single small `.glb`, draws its screen face at runtime on a canvas, and speaks a short summary of each finished reply through **Kokoro-82M via kokoro-js** (Apache-2.0 code and weights) with a light robot effect chain. This works with the Claude Code sessions Sev already runs, both in the terminal and in the desktop app's Code tab, on his subscription, because the companion never authenticates: Claude Code does that, and it simply POSTs every event to the companion. The hooks give a reliable picture of greet, thinking, tool use, browsing, needing permission, done and error. `Stop` even carries `last_assistant_message` so the reply can be read aloud without parsing transcripts. Two limits shape the design. First, the ordinary desktop Chat tab and Cowork sessions cannot be observed this way, so the companion fronts *Code* sessions only. Second, community bug reports say hooks sometimes don't fire in desktop builds on Windows, so the first thing to build is a two-hour spike that proves hooks reach a localhost server from Sev's own desktop app. Everything else in the stack is well-trodden: a 2026 Electron Claude Code pet (Clawd on Desk) already runs the same hook-to-overlay pipeline, and the 3D asset is a sub-300 KB file Sev can script end to end through the Blender MCP server he already has. Voice comes later and costs nothing but CPU. Voice input stays out of scope for now, since Claude Code already ships `/voice` dictation.

## Claude Code's 33 hook events carry everything the robot needs to act

Hooks are the supported integration route, and their 2026 form fits this product closely. The hooks reference now lists **33 events**, plus a native **`http` handler type** that POSTs the event JSON straight to a URL. The documentation's own example is `http://localhost:8080/hooks/pre-tool-use` ([Hooks reference](https://code.claude.com/docs/en/hooks)). That removes the helper script, the shell, PATH and quoting, which are exactly the problems the docs warn about on Windows: desktop doesn't read PowerShell profiles, and `.cmd` shims fail in exec form ([Desktop docs](https://code.claude.com/docs/en/desktop), [Hooks reference](https://code.claude.com/docs/en/hooks)). A connection failure on an `http` hook is non-blocking unless `onFailure: "block"` is set, so a closed companion never breaks a Claude session ([Hooks reference](https://code.claude.com/docs/en/hooks)). The one rule is that the endpoint must answer immediately. `async` exists only for `command` hooks, and http hooks have a 600-second default timeout, so a slow response would stall Claude.

The events map onto Sev's behaviours with little interpretation. Every payload carries `session_id`, `cwd`, `transcript_path` and `permission_mode`, so the companion can track several sessions at once and know when auto or bypass mode means permission prompts will rarely arrive. `SessionStart` triggers the greeting. `UserPromptSubmit` starts thinking. `PreToolUse`/`PostToolUse`, keyed by `tool_use_id`, bracket each tool call, and `PostToolBatch` closes parallel batches. `PermissionRequest` fires immediately when a decision is needed; `Notification` with `permission_prompt` fires after about six seconds without input, and `idle_prompt` after about 60 seconds. `Stop` ends the turn, `StopFailure` reports API errors such as `rate_limit`, `SubagentStart`/`SubagentStop` expose subagents, and `SessionEnd` triggers the goodbye ([Hooks reference](https://code.claude.com/docs/en/hooks)). The docs explicitly recommend that read-aloud hooks use `Stop`'s **`last_assistant_message`** rather than the transcript file, which "isn't guaranteed to include the final message at Stop time" ([Hooks reference](https://code.claude.com/docs/en/hooks)). A newer **`MessageDisplay`** event delivers assistant text in batches of completed lines (not tokens) while it is displayed. That gives "explaining" bubbles near-real-time text without the SDK ([Hooks reference](https://code.claude.com/docs/en/hooks)).

No hook exposes extended-thinking content or a "generating" heartbeat. "Thinking" is therefore inferred: the gap after `UserPromptSubmit`, or after a tool finishes, until the next `PreToolUse` or `MessageDisplay`. A user's Esc interrupt also has no event of its own, so the state machine needs timeouts that fall back to idle. The browser behaviour, where the robot sits on a window edge and points, keys off tool names. `WebFetch`/`WebSearch` come from the docs. The other names were observed first-hand in a live desktop Code-tab session on this machine during research, not taken from documentation: `mcp__Claude_Browser__*` for the desktop app's built-in Browser pane, `mcp__claude-in-chrome__*` for the Chrome extension, `mcp__plugin_playwright_playwright__browser_*`, and `mcp__computer-use__*`. A regex like `^(WebFetch|WebSearch|mcp__Claude_Browser__|mcp__claude-in-chrome__|mcp__.*playwright.*__browser_)` covers them. The desktop docs confirm the built-in Browser pane exists and that Claude by default "auto-verifies changes after every edit" with it ([Desktop docs](https://code.claude.com/docs/en/desktop)), so browsing will be frequent. One practical consequence, inferred: for `mcp__Claude_Browser__*` the window to point at is the Claude desktop window itself, whose pane holds the page. For Chrome tools it is the Chrome window.

Speaking a whole Claude Code reply aloud would be tiring. Community TTS hooks already speak a summary or the first sentence: claude-code-tts speaks the first sentence from a `Stop` hook, and cc-vox speaks a summary after each response, though these come from search listings with the repositories unread ([listing](https://enterprisedna.co/directories/mcp/ybouhjira-claude-code-tts), [cc-vox](https://github.com/BestSithInEU/cc-vox)). The cleanest version uses a plugin **output style** (`output-styles/<name>.md`) that asks Claude to end each reply with one tagged spoken line, which the companion extracts from `last_assistant_message` ([Plugin components](https://code.claude.com/docs/en/plugins/components)). A more structured alternative is a `say(text, emotion)` tool on a local MCP server bundled in the same plugin, but tool calls cost tokens and can trigger permission prompts.

### Packaging as a plugin, and why not the Agent SDK

All the Claude-side pieces fit in one Claude Code plugin. It can bundle `hooks/hooks.json` (including `http` hooks), an output style, a skill and a `.mcp.json` server. It is distributed from a public GitHub repo with a `.claude-plugin/marketplace.json` and installed with `claude plugin marketplace add <owner>/<repo>` and `claude plugin install` ([Plugin components](https://code.claude.com/docs/en/plugins/components), [Create a marketplace](https://code.claude.com/docs/en/plugin-marketplaces)). The desktop app can install plugins too, scoped to user, project or local ([Desktop docs](https://code.claude.com/docs/en/desktop)). Existing pets show the etiquette worth copying: opt-in installation of tagged hook entries (woofy merges five tagged hooks), auto-registration on start (IMMINJU/claude-pet), and an explicit uninstall command (claudlet) ([woofy](https://github.com/dashty8/woofy), [IMMINJU/claude-pet](https://github.com/IMMINJU/claude-pet), [claudlet](https://pypi.org/project/claudlet/1.3.0/)).

The Agent SDK is the wrong core for this product, even though it streams the richest signal, including partial deltas. It runs its *own* session rather than following the ones Sev already uses, and Anthropic states that "unless previously approved, Anthropic does not allow third party developers to offer claude.ai login or rate limits for their products, including agents built on the Claude Agent SDK" ([Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)). For Sev's personal use, SDK and `claude -p` usage on his login still draw from subscription limits ([Claude Help Center](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan)). A public release built that way, however, would need users' own API keys. The hook route sidesteps the issue entirely because the companion never touches credentials. The raw Messages API is further away still: a separate pay-per-token product with none of Sev's sessions, skills, tools or permission UI.

### What remains unverified on the integration side

Four claims matter for building and were not confirmed. **First**, the hooks reference reportedly says hooks fire in the Desktop app as well as the terminal. That came from a search summary; the passage itself wasn't read ([Hooks reference](https://code.claude.com/docs/en/hooks)). The desktop docs do treat `~/.claude/settings.json` as applying to local Code-tab sessions ([Desktop docs](https://code.claude.com/docs/en/desktop)). Even so, community bug reports describe hooks that stop firing after editing `settings.local.json` on Desktop 2.1.156 for Windows, `SessionStart` not firing in GUI panes, and `PreToolUse` hooks registered but never executing on v2.1.219 for Windows. Whether those bugs are fixed is unknown ([64699](https://claudeissues.com/issue/64699-hooks-stop-firing-entirely-after-editing-settings-local-json-desktop-2-1-156-win), [16763](https://claudeissues.com/issue/16763-sessionstart-hooks-dont-fire-when-opening-gui-panes), [85904](https://claudeissues.com/issue/85904-bug-pretooluse-hooks-are-registered-and-listed-by-hooks-but-never-execute-v2-1-2)). **Second**, it is unclear whether loopback URLs need entries in the `allowedHttpHookUrls` setting by default, or need user approval when installed from a plugin ([Hooks reference](https://code.claude.com/docs/en/hooks)). **Third**, whether `MessageDisplay` fires per line batch in the desktop GUI, or once per message as in non-interactive runs, needs an empirical test. **Fourth**, a third-party guide says the Code tab runs its own app-managed copy of Claude Code, whose version can differ from the terminal `claude` ([developertoolkit.ai](https://developertoolkit.ai/en/claude-code/build/desktop-app/)). The companion must therefore tolerate missing events and fields, and should ship a "send test event" self-check. Cowork reads its configuration from claude.ai rather than `~/.claude` ([Desktop docs](https://code.claude.com/docs/en/desktop)), and community reports say Cowork ignores user hooks ([claudeissues.com](https://claudeissues.com/platform/macos-hooks)). Assume Cowork, like plain Chat, is invisible to the companion.

## Electron wins the overlay because click-through keeps reporting the cursor

The overlay must be transparent, always on top, unfocusable, and click-through everywhere except the robot and its bubble. Only Electron documents a mechanism that keeps the app informed while clicks pass through. `setIgnoreMouseEvents(true, {forward: true})` still forwards mouse-move messages on Windows and macOS, so the renderer sees `mouseenter`/`mouseleave` over the character and can turn ignoring back off ([Electron window customization](https://www.electronjs.org/es/docs/latest/tutorial/window-customization)). Tauri v2's `set_ignore_cursor_events` is all-or-nothing for the whole window, and once it is on, no mousemove reaches the webview. Projects poll the global cursor from Rust instead; one polls every 120 ms ([tauri-plugin-polygon](https://docs.rs/crate/tauri-plugin-polygon/latest/source/src/desktop.rs), [CodeWalkers](https://deepwiki.com/you-want/CodeWalkers/2.1.1-window-and-click-through-logic)). Open issues cover enter/exit detection and Windows child-window click-through ([tauri#9250](https://github.com/tauri-apps/tauri/issues/9250), [tauri#11461](https://github.com/tauri-apps/tauri/issues/11461)). Godot 4.6 is a real native-3D alternative, but forum threads report passthrough sprites disappearing on 4.6.1, dark or white screens and taskbar glitches on 4.4.1, and monitor-sized always-on-top windows being promoted to exclusive fullscreen ([forum](https://forum.godotengine.org/t/mouse-passthrough-polygon-method-couses-my-animated-sprite-to-disappear/135419), [forum](https://forum.godotengine.org/t/need-help-visual-glitch-of-windows-tool-bar-and-dark-screen-using-transparent-and-passthrough-windows/116526), [forum](https://forum.godotengine.org/t/window-transparency-sometimes-not-working/86812)). Unity needs Win32 DWM hacks, and users report they can switch click-through on but not back off ([Unity Discussions](https://discussions.unity.com/t/how-to-make-a-unity-game-window-transparent-and-click-through/1704947)).

| Stack | Click-through model | Installer | Main risk for this project |
|---|---|---|---|
| **Electron + three.js** (recommended) | Toggle + `forward:true` mouse-move on Win/macOS | ~80–200 MB | Size; macOS `forward` disputed by one project's notes |
| Tauri v2 + three.js | Whole-window toggle, poll cursor in Rust | a few MB–~10 MB | Open click-through issues; three different OS webviews |
| Godot 4.6 | Passthrough polygon or per-pixel alpha toggle | tens of MB | Reported Windows passthrough/render glitches |
| Unity 6 | Win32 `WS_EX_LAYERED \| WS_EX_TRANSPARENT` | large | Windows-only hacks, fragile toggling |

The size gap is real: one Windows 11 test measured 1.05 MB versus 106.1 MB for the same app. RAM claims, on the other hand, are inconsistent, with measured idle figures of 109 versus 128 MB, and one 2026 analysis notes the "5x less RAM" claim has no reproducible benchmark ([Better Stack](https://betterstack.com/community/guides/scaling-nodejs/tauri-vs-electron-vs-deno-vs-electrobun/), [moklabs](https://moklabs-research.pages.dev/reports/technology/2026-03-20-tauri-vs-electron-desktop-framework-decision)). For a companion that runs all day, about 100 MB of disk buys the documented mechanism, one Chromium everywhere, and the most direct prior art. **Clawd on Desk** is an Electron transparent always-on-top pet with 12 animated states, auto-registered Claude Code hooks and permission bubbles, at roughly 5,400 stars in July 2026. That comes from secondary write-ups; its licence and IPC weren't confirmed ([brightcoding](https://blog.brightcoding.dev/2026/09/29/rullerzhou-afkclawd-on-desk-desktop-pet-for-ai-coding-agents)). **AIRI** is an Electron + three.js VRM desktop companion, licensed mostly MIT ([AIRI](https://mintlify.com/moeru-ai/airi/introduction)). Note that the overlay research relied on search-result extracts rather than full doc pages, and current Electron and Tauri version numbers were not confirmed.

The window design follows from those constraints. Use a **small window**, about twice the robot's bounding box plus room for the bubble, moved by the main process, rather than one transparent window spanning the desktop. That avoids per-monitor DPI mismatch and compositing a huge transparent surface, and it limits the damage if click-through misbehaves (inference; no benchmark was found). Create it with `alwaysOnTop` at the `"screen-saver"` level and `showInactive()` so it never steals focus ([taskbar client sample](https://gitfront.io/r/Elendiar/21SQq6UV13ja/production-taskbar-client/blob/src/main/mainWindow.js)). Add `focusable: false`, which on Windows also implies `skipTaskbar` ([Electron BaseWindow](https://electronjs.org/fr/docs/latest/api/base-window)). Add a tray icon for control. Hit-test the robot by raycasting against the three.js mesh, and toggle ignore accordingly. Hide over fullscreen games, because overlays there are unreliable in every stack ([SO mirror](https://coderapp.vercel.app/answer/37766911)).

Walking the taskbar and sitting on window edges need knowledge of the desktop, and Windows exposes all of it. `get-windows` (formerly `active-win`) returns window titles, ids and bounds across Windows, macOS and Linux ([get-windows](https://www.Github.com/sindresorhus/get-windows)). For precise edges, a small koffi FFI layer in the Electron main process should use `DWMWA_EXTENDED_FRAME_BOUNDS`, because `GetWindowRect` includes invisible resize borders. It should read the taskbar from `SHAppBarMessage(ABM_GETTASKBARPOS)` and subscribe to `EVENT_SYSTEM_FOREGROUND`/`EVENT_OBJECT_LOCATIONCHANGE`. That design is inference from Win32 practice; the specific libraries were not individually verified. Shimeji-style ports are the behavioural reference for "the floor is the taskbar top or a window's top edge", but Shimeji Desktop Mascot is GPLv3 ([SourceForge](https://sourceforge.net/p/shimeji-desktop/)): study it, don't copy it. Cross-platform limits are clear. macOS returns window bounds without permission but hides titles unless Screen Recording is granted ([Apple forum](https://developer.apple.com/forums/thread/839069)). Wayland forbids global positioning and has no standard always-on-top protocol ([freedesktop wayland#305](https://gitlab.freedesktop.org/wayland/wayland/-/issues/305)), and `wlr-layer-shell` is missing on GNOME's Mutter ([layer-shell docs](https://isaacfreund.com/docs/wayland/wlr-layer-shell-unstable-v1)). Linux should ship as "full features on X11/XWayland, roam-in-bounds without window sitting on Wayland".

## A 12-bone rigid rig and a canvas face keep the Blender pipeline to one script

The character is a box with tubes, so the pipeline should be deterministic, scripted and re-runnable, not sculpted. Build it from primitives (aim for 2,000 triangles or fewer) with a **hand-made armature of about 12 bones**: `root`, `body`, upper/lower arms and legs, and optional hands and feet. Bind each rigid part to one bone at weight 1.0, and skip Rigify, which generates hundreds of bones and needs deform-only export hygiene ([Blender manual, Rigify](https://docs.blender.org/manual/en/latest/addons/rigging/rigify/index.html)). The glTF exporter carries Principled BSDF, unlit materials, keyframe, shape-key and skinning animation ([Blender 5.1 manual, glTF](https://docs.blender.org/manual/en/5.1/addons/import_export/scene_gltf2.html)). Flat colours export cleanly, one material per colour. A Blender toon ramp does not, so recreate banded shading at runtime with `MeshToonMaterial` if wanted. Model the screen as a separate named `Screen` quad with 0–1 UVs so the runtime can swap its material, and add an empty `bubble_anchor` above the head.

Animation organisation has one well-known trap. Since Blender 4.4, Actions are slotted and the exporter merges by Action rather than NLA track names ([Blender 4.4 release notes](https://developer.blender.org/docs/release_notes/4.4/pipeline_assets_io/)). In the default "Actions" mode, however, an action that is neither active nor on an NLA track "is not exported" ([Blender 5.1 manual, glTF](https://docs.blender.org/manual/en/5.1/addons/import_export/scene_gltf2.html)). That produces the classic "my clip is missing from the .glb" bug. The build script should push every action to its own NLA track, key every bone on frame 1, and export with sampling on, **Optimize Animation Size**, **Force keeping channels for bones** and **Reset pose bones between actions** enabled ([Blender 5.1 manual, glTF](https://docs.blender.org/manual/en/5.1/addons/import_export/scene_gltf2.html)). Keep clips in place. Code moves the robot along the taskbar, because neither glTF nor three.js `AnimationMixer` has root motion.

**Blender 5.x API changes are the biggest risk for AI-written scripts.** Blender 5.0 moved bone visibility and selection to pose bones, with the note that "these changes break backwards compatibility for the Python API". It also changed how Python-created drivers are keyed ([Blender 5.0 animation notes](https://developer.blender.org/docs/release_notes/5.0/animation_rigging/)). A secondary guide reports that 5.0 removed the legacy `action.fcurves`/`action.groups` API in favour of `action.slots`/`action.layers` → strips → channelbags. This was not confirmed on the official Python API notes page ([Cinevva guide](https://app.cinevva.com/guides/blender-5-for-game-artists)). Older training data writes exactly the code that breaks. The official Blender Lab MCP server Sev has connected exposes `execute_blender_code`, scene summaries, screenshot and render tools, and bundled API-doc search. Its own guidance is to inspect the scene first, prefer `bpy.ops`, set mode and selection explicitly, and return structured data ([Blender Lab MCP readme](https://projects.blender.org/lab/blender_mcp/raw/branch/main/readme.md)). The working pattern is three idempotent files kept in the repo: `build_robot.py`, `build_actions.py` (pose tables to keyframes, checked against the bundled 5.x docs) and `export.py`. Run them in small steps with a screenshot after each. Validate the approach first on a cube with two actions. LLM-driven Blender is good at this construction work and weak at judging appeal, so Sev should hand-tune timing on the two or three hero clips. AI mesh generators and Mixamo don't help here: Adobe says Mixamo is for bipedal humanoids and may fail on "deformed" proportions ([Mixamo FAQ](https://helpx.adobe.com/creative-cloud/faq/mixamo-faq.html)).

At runtime, three.js needs only `GLTFLoader`, one `AnimationMixer` and a table-driven state machine. Use `LoopOnce` with `clampWhenFinished` for gestures and `crossFadeTo` for transitions ([three.js AnimationAction](https://threejs.org/docs/pages/AnimationAction.html)). A forum report says `crossFadeTo` only works once the target action is reset, weighted and playing ([three.js forum](https://discourse.threejs.org/t/animationaction-crossfadeto-not-working/63467)). For a stop-motion toy feel, advance the body mixer in steps of 8–12 fps while the face and lip-sync run at 30–60 fps. An orthographic camera keeps the screen face undistorted and makes bubble placement a simple scale-and-offset. Watch for r185's `updateWorldMatrix` change, which reportedly broke some apps ([three.js forum](https://discourse.threejs.org/t/r185-updateworldmatrix-update-broke-apps/93444)).

The **face is drawn, not authored**. Use a 256×192 canvas as a `CanvasTexture` on an unlit material on the `Screen` mesh, with parametric eyes, mouth and glyphs (?, …, zzz, X), a random blink every 2–6 s, and a gaze offset toward the target window ([three.js CanvasTexture](https://threejs.org/docs/#api/en/textures/CanvasTexture)). That gives unlimited expressions without sprite-sheet combinatorics. Speech bubbles should be **HTML/CSS** positioned from the projected `bubble_anchor` (`Vector3.project`), which gives crisp DPI-correct text, markdown and buttons for free ([three.js Vector3](https://threejs.org/docs/#api/en/math/Vector3.project)). Pointing layers eye gaze, a body yaw of up to about 20–25° and a procedural upper-arm rotation of `atan2(d.y, d.x)` toward the target rectangle after the clip updates. The proposed mapping for Sev's states is a design proposal, not sourced guidance:

| Claude signal | Body | Face | Priority |
|---|---|---|---|
| `SessionStart` | appear → `wave` → `idle` | happy | one-shot |
| `UserPromptSubmit`, tool gaps | `think` loop (≥0.3 s debounce) | eyes up, "…" | medium |
| `PreToolUse` (generic) | `think`/`work` loop | focused, tool badge | medium |
| Browser tool names | `walk` to window edge → `sit_idle`/`point` | curious, gaze at window | medium |
| `MessageDisplay` batches | `talk` + speech bubble | lip-sync or text cadence | high |
| `PermissionRequest` / `permission_prompt` | `wave`/ask loop + persistent bubble | "?" | high |
| `Stop` | `happy` one-shot → `idle`, speak summary | big smile | one-shot |
| `idle_prompt`, long idle | taskbar walk, then `sit_down` → `sit_idle` → sleep | sleepy | low |
| `StopFailure` | code-driven shake | worried/X eyes | top |
| `SessionEnd` | `wave` → disappear | eyes close, screen off | top |

The asset budget is tiny: **2,000 triangles or fewer, 16 bones or fewer, 12 clips or fewer, and a .glb of 300 KB or less**, with no Draco, since its WASM decoder would outweigh the model ([Blender 5.1 manual, glTF](https://docs.blender.org/manual/en/5.1/addons/import_export/scene_gltf2.html)). These are engineering estimates to confirm on the first export. The real performance budget is the transparent window, which means render-on-demand and pausing when hidden.

## Kokoro is the only small voice with Apache-licensed code and weights

For free, fully open-source speech, **Kokoro-82M** stands alone: both weights and code are Apache-2.0, and it has 82M parameters ([HF Kokoro-82M](https://huggingface.co/hexgrad/Kokoro-82M), [npm kokoro-js](https://npmjs.com/package/kokoro-js)). **kokoro-js** runs it in Node (CPU) or in the Electron renderer (WASM/WebGPU) with no Python sidecar, offers fp32-to-q4 dtypes, and has a `TextSplitterStream` that turns streaming text into audio chunks ([kokoro-js README](https://cdn.jsdelivr.net/npm/kokoro-js@1.2.0/README.md)). Two caveats are worth knowing. v1.0 from January 2025 is still the latest official release, and part of the training data is synthetic audio from closed commercial TTS providers ([HF Kokoro-82M](https://huggingface.co/hexgrad/Kokoro-82M)). No primary benchmark of Kokoro's real-time factor on a typical Windows laptop was found, so measure it in Phase 0 or 4.

The alternatives all trip on a licence or a runtime. Piper development moved to **OHF-Voice/piper1-gpl**, which is GPL-3.0-or-later. The project grants no rights over voices ([LICENSING.md](https://github.com/OHF-Voice/piper1-gpl/blob/main/docs/LICENSING.md)), and the popular `lessac`-derived voices are effectively research-only. The public-domain `en_US-ljspeech` voice ([model card](https://huggingface.co/rhasspy/piper-voices/raw/main/en/en_US/ljspeech/high/MODEL_CARD)) can still be run through **sherpa-onnx** (Apache-2.0, with Node and Windows support) without linking GPL code ([sherpa-onnx](https://github.com/k2-fsa/sherpa-onnx)). Kyutai **Pocket TTS** is CC-BY-4.0 weights and Python-only officially ([HF pocket-tts](https://huggingface.co/kyutai/pocket-tts)). **KittenTTS 2** weights sit under a non-OSI community licence ([KittenTTS](https://github.com/KittenML/KittenTTS)), and **Supertonic** is OpenRAIL-M with use restrictions ([HF Supertonic](https://huggingface.co/Supertone/supertonic/blob/main/README.md)).

No voice is labelled childlike. The best starting points from Kokoro's graded list are **af_heart (A)**, **af_bella (A-)** and **af_nicole (B-)**, with **af_sky** as a lighter but low-data option ([VOICES.md](https://huggingface.co/hexgrad/Kokoro-82M/blob/main/VOICES.md)). The robot character comes from post-processing in Web Audio with **Tone.js** `PitchShift` and `BitCrusher` ([Tone.js PitchShift](https://tonejs.github.io/docs/14.7.30/PitchShift)). A suggested untested starting chain is +3 to +5 semitones, an 8–10-bit crush, faint 30–60 Hz tremolo and a slight highpass, tuned by ear. Lip-sync for a line mouth needs no phonemes. Route the audio through an `AnalyserNode`, smooth the RMS, and quantise it to four mouth levels at about 12 Hz. Live2D's own tutorial uses volume as its baseline method ([Live2D docs](https://docs.live2d.com/en/cubism-sdk-tutorials/native-lipsync-from-wav-web)). If viseme timing is wanted later, **HeadTTS** (MIT) wraps a timestamped Kokoro model and outputs visemes without GPL eSpeak ([HeadTTS README](https://unpkg.com/@met4citizen/headtts@0.2.0/README.md)). Web Speech `speechSynthesis` remains a zero-setup fallback using OS voices, but those voices are proprietary ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/SpeechSynthesis)).

Voice **input** is a future phase only. Claude Code already has `/voice` dictation with push-to-talk. It streams audio to Anthropic for transcription, needs a Claude.ai account, and doesn't consume tokens ([Voice dictation](https://code.claude.com/docs/en/voice-dictation)). The two-way "voice mode" in the Claude apps is not available in Claude Code or Cowork ([Help Center](https://support.claude.com/en/articles/11101966-use-voice-mode)). So the companion pairs naturally with dictation going in and its own TTS coming out.

## Keep the robot, its name and its parts clearly original

Because the character comes from Sev's own sketches, with its own name and colours, it needs only a few rules, not an IP study. Keep its silhouette, palette, face style and name clearly distinct from the well-known cartoon console character. Never use, derive from or ship fan-made models of that character. These exist on Sketchfab and are reachable through the community Blender MCP's asset import, and an uploader's CC licence doesn't grant the character design ([ahujasid/blender-mcp](https://github.com/ahujasid/blender-mcp)). Never prompt an AI generator or voice-cloner with the character's name or a real voice actor. ## Conclusion

The hard part of this project is not 3D, voice or even Windows overlays; each has a proven, permissively licensed path. The hard part is the thin seam between the desktop app's bundled Claude Code build and a localhost server, and whether every event Sev's design leans on actually crosses it. That inverts the usual build order. Instead of modelling the robot first, Sev should spend the first afternoon proving `Stop`, `PreToolUse` and `PermissionRequest` reach a 20-line server from his real desktop sessions. He should also prove the Blender 5.x exporter emits two named clips from a scripted cube. Once those two spikes pass, the remaining risk is taste, not feasibility.

A second insight is that "fronting Claude" means fronting **Code** sessions specifically. The Chat tab and Cowork expose no event stream, so a companion that claims to watch "Claude" generally would overpromise. Built on hooks and shipped as a plugin plus app, the companion also stays on the right side of Anthropic's third-party login rule for a public release. Users bring their own authenticated Claude Code, and the robot just listens.

## Recommended architecture

**Integration.** Claude Code native `http` hooks on `SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `PostToolBatch`, `PermissionRequest`, `Notification`, `MessageDisplay`, `Stop`, `StopFailure`, `SubagentStart`/`SubagentStop` and `SessionEnd` all POST to `http://127.0.0.1:<port>/event` with a token header. The companion answers 2xx immediately. It ships as a Claude Code plugin (hooks plus a "spoken summary line" output style) through a GitHub marketplace, with a tagged opt-in installer and an uninstaller for users who prefer `~/.claude/settings.json`. Sessions are tracked by `session_id`. There is no Agent SDK and no API key.

**Overlay stack.** Electron (main process: HTTP server, single-instance lock, tray, autostart, koffi Win32 helpers for window rects and the taskbar), with a small transparent `alwaysOnTop("screen-saver")`, `focusable:false`, `showInactive` window that moves with the robot. Click-through uses `setIgnoreMouseEvents(true,{forward:true})` toggled by a mesh raycast. The renderer is three.js with an orthographic camera, `GLTFLoader`, one `AnimationMixer` stepped at 8–12 fps, a table-driven FSM, a `CanvasTexture` face and HTML/CSS bubbles.

**Animation pipeline.** Blender 5.x driven by the Blender MCP server through `build_robot.py` / `build_actions.py` / `export.py`. The rig is 12 bones with rigid binding. Clips are one Action each, pushed to NLA, and exported as a single `.glb` of 300 KB or less in Actions mode with reset-pose and keep-channels on.

**Voice out.** kokoro-js (Kokoro-82M, Apache-2.0) in the renderer or a Node worker, voice af_heart/af_bella, through a Tone.js pitch/bitcrush chain, with AnalyserNode amplitude lip-sync. It speaks the tagged summary line from `Stop.last_assistant_message`, with `speechSynthesis` as a fallback and a mute hotkey.

**Voice in (later phase).** Use Claude Code's built-in `/voice` dictation. A companion-owned push-to-talk is a future item.
